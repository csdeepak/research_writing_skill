## Introduction

Software is, for most practical purposes, the most general interface through which anything -- human or machine -- can act on the world: writing code, running it, and browsing the web already cover an enormous range of tasks. As large language models have become capable enough to drive *agents* -- systems that repeatedly observe the state of an environment and choose an action to take in it, rather than producing one fixed output -- a natural direction is to give such agents this same general interface, so that one agent design might, in principle, act on many kinds of task rather than one. A platform built on exactly this premise, OpenHands, is already in wide use: it is released under a permissive open-source license and had accumulated more than 2,100 code contributions from over 188 contributors and 32,000 GitHub stars at the time it was described.

Building that platform, however, does not by itself answer whether one agent built on it can act as a genuine generalist. Prior open agent frameworks provide some of the needed infrastructure -- an interface for the agent to act through, an environment to act in, a way for users and agents to communicate -- but, on their own developers' or on this platform's account, at uneven depth: one framework, AutoGen (Wu et al., 2023), adds real code-execution capability to a conversational interface "though with stateless command execution," and others, such as LangChain (Chase, 2022), are described as offering only "foundational building blocks with basic runtime support" {C019}. Separately, agents built for one demanding task category, such as resolving real GitHub issues, have shown that a carefully designed set of task-specific tools can matter a great deal for solving complex problems (Yang et al., 2024) -- but that observation was established, and those systems were evaluated, within a single task category, not across qualitatively different ones {C018}.

This leaves an open question: can one open platform, and one generalist agent built on it with a single fixed prompt, remain competitive across software engineering, web browsing, and other reasoning/tool-use tasks at once, rather than requiring a bespoke agent design for each?

OpenHands answers this with an event-stream architecture connecting users, agents, and the environment; a Docker-sandboxed runtime exposing a shell, a Python interpreter, and a browser; an extensible tool library (an *agent-computer interface*, or ACI); and the ability for agents to delegate subtasks to one another. On top of this infrastructure sits a hub of more than ten community-contributed agents, including a generalist agent whose actions are themselves executable code or browser commands rather than calls to a fixed menu of tools -- a design referred to as CodeAct (Wang et al., 2024a) {C017}. The platform's own evaluation harness tests this generalist agent, with one fixed prompt and no benchmark-specific modification, on 15 benchmarks spanning software engineering, web browsing, and miscellaneous reasoning and tool-use assistance.

The headline finding is that this single agent design is competitive -- though, as we show, rarely the single best system on any one benchmark -- in every one of the three categories at once: for example, it resolves 26.0% of SWE-Bench Lite issues (Jimenez et al., 2024), within the range of specialized open coding agents {C001}; it completes 15.5% of WebArena's browsing tasks (Zhou et al., 2023a) {C004}; and it reaches 52.0% accuracy on GPQA's graduate-level science questions (Rein et al., 2023), above both non-expert humans and the language-model baselines shown {C006}. No comparison baseline in the paper's own tables is evaluated across more than one of the three categories {C015}. We take this combination -- one unmodified design, evaluated everywhere, against baselines that are each evaluated once -- as evidence for the platform's stated goal of generality {C016}.

The rest of the paper works through this evidence and its limits. We describe the platform's architecture and the evaluation's protocol, then present results by category before drawing them together into a single cross-category pattern. We return, in the Discussion, to where the agent is not the best performer, and to what the platform's design does and does not establish about the safety of increasingly capable, more autonomous agents. In the Limitations, we return to the statistical status of these numbers -- no benchmark in this evaluation reports repeated-run variance -- and to how much the codebase evaluated here has since changed.
